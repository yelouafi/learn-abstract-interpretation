At the end of chapter 2 we had one set of integers per variable, but those sets can be infinite. In this chapter we summarize each set by a single **sign**, rebuild arithmetic, tests and control flow on signs, and get a working analyzer. Every idea in later chapters is a refinement of what we do here.

## Summarize a set by its sign

Instead of “$x \in \{3, 7, 12\}$” we keep only “$x$ is positive”. We need five abstract values:

| Abstract value | Meaning: the set of integers it stands for |
| --- | --- |
| $+$ | $\{1, 2, 3, \dots\}$ |
| $0$ | $\{0\}$ |
| $-$ | $\{\dots, -3, -2, -1\}$ |
| $\top$ ("top") | all of $\mathbb{Z}$: we know nothing |
| $\bot$ ("bottom") | $\varnothing$: no value at all, so this code is unreachable |

The "meaning" column is a function, called the **concretization** $\gamma$ (gamma): $\gamma(+) = \{1, 2, \dots\}$, $\gamma(\top) = \mathbb{Z}$, and so on. In the other direction, the **abstraction** $\alpha$ (alpha) takes a set of integers to the *most precise* sign that covers it: $\alpha(\{3, 7, 12\}) = +$, $\alpha(\{0\}) = 0$, $\alpha(\{-1, 5\}) = \top$, $\alpha(\varnothing) = \bot$.

In code, an abstract value is just a string:

```ts
type Sign = 'bot' | 'neg' | 'zero' | 'pos' | 'top';
```

A handful of bits now stands for a possibly infinite set. The rest of this chapter is about computing with these strings without ever going back to sets.

## Ordering by precision

Some abstract values say more than others. $+$ is more precise than $\top$, because $\gamma(+) \subseteq \gamma(\top)$. We write $+ \sqsubseteq \top$ (“$+$ is below $\top$”). This ordering is drawn as a **Hasse diagram**: precise at the bottom, vague at the top.

<SignLattice />

Two operations on this diagram matter, and you can try both above:

- The **join** $a \sqcup b$ is the lowest element above both. It answers "I have either an $a$ or a $b$; what do I know?". Merging $+$ and $0$ gives $\top$: the domain cannot say "non-negative", so it rounds up to "anything".
- The **meet** $a \sqcap b$ is the highest element below both. It answers "I know it is an $a$ *and* a $b$". The meet of $+$ and $\top$ is $+$; the meet of $+$ and $-$ is $\bot$ (impossible).

The analyzer uses join where control flow merges (after an `if`, at a loop head) and meet when a test tells it something new (`x > 0` means "whatever x was, and positive").

<Insight title="lattices">

A **partial order** $\sqsubseteq$ is reflexive, transitive and antisymmetric, like $\subseteq$ on sets. It is *partial* because some pairs are incomparable: neither $- \sqsubseteq +$ nor $+ \sqsubseteq -$.

A **lattice** is a partial order in which every pair $a, b$ has a least upper bound $a \sqcup b$ and a greatest lower bound $a \sqcap b$. The sets of integers, ordered by $\subseteq$ with $\cup$ and $\cap$, form a lattice; the signs form a much smaller one. Abstract interpretation is about relating the two.

</Insight>

α and γ are tied together by one property, which you can check on the widget: for any set $S$ of integers and any sign $a$,

$$
\alpha(S) \sqsubseteq a \quad\iff\quad S \subseteq \gamma(a)
$$

In words: “$a$ is a correct description of $S$” means the same thing on both sides, and $\alpha(S)$ is the best correct description. This is a **Galois connection**, the central tool of chapter 4. For now, keep the slogan: **α picks the best description, γ says what a description means.**

## Abstract arithmetic

To analyze `y = x * 2` we need to multiply *signs*. Start with what you already know from school, and answer each question for **any** numbers with those signs:

- positive × positive? Always **positive**.
- negative × positive? Always **negative**.
- zero × anything? Always **zero**.
- positive + positive? Always **positive**.
- positive + negative? **It depends**: $5 + (-3) = 2$, $3 + (-3) = 0$, $3 + (-5) = -2$. Any sign is possible, so the only safe answer is $\top$.

That is all abstract arithmetic is. Here is every answer, for the four operators. The tables are generated from the real implementation when the site is built:

<SignTables ops={['+', '-', '*', '/']} />

Some entries to read carefully:

- $(+) + (-) = \top$: the sign of the sum depends on the sizes of the numbers, which we threw away.
- $\top \times 0 = 0$: anything times zero is zero, so even total ignorance gives a precise answer.
- $(+) \div (+) = \top$: division truncates, so $1 \div 2 = 0$ but $5 \div 2 = 2$. The true answer is "zero or positive", and this domain has no value meaning exactly that, so it must say $\top$.
- $x \div 0 = \bot$: there is no result, because the program crashes. The analyzer reports an alarm whenever the divisor *may* be zero.
- $\bot$ in, $\bot$ out: no values in, no values out.

### One recipe for every entry: split into cases

The tables are not written out one by one. They all come from one recipe that you have probably used without naming it. Every integer is **negative, zero or positive**. Call these three the **basic signs**. Each abstract value covers some of them: $+$ covers just *positive*, $\top$ covers all three, $\bot$ covers none.

To compute `a op b`:

1. **Split** each side into the basic signs it covers.
2. **Work out each combination**: for a negative and a positive, which signs can the result have? These are the school facts from the list above.
3. **Summarize** all the signs you collected as one abstract value: none gives $\bot$, one gives that sign, two or three give $\top$.

Worked example, $\top + (+)$:

| | b positive |
| --- | --- |
| **a negative** | $-$, $0$ or $+$ (e.g. $-3 + 5 = 2$, $-3 + 3 = 0$, $-5 + 3 = -2$) |
| **a zero** | $+$ (e.g. $0 + 2 = 2$) |
| **a positive** | $+$ (e.g. $2 + 3 = 5$) |

The collected signs are $\{-, 0, +\}$, which summarizes as $\top$. Try other combinations in the calculator below: it runs exactly this recipe, with real example computations in every cell. Note the case $(+) \div (+)$: the collected signs are $\{0, +\}$, and step 3 has to **round them up** to $\top$. That rounding is where this domain loses precision, and chapter 4 removes it.

<CaseSplit a="top" op="+" b="pos" />

In code, the recipe is three small functions. This snippet is complete; the real code has the same structure with all four operators:

```ts
type BasicSign = 'neg' | 'zero' | 'pos';
type Sign = 'bot' | BasicSign | 'top';

// 1. Split: which basic signs does an abstract value cover?
function cases(s: Sign): BasicSign[] {
  return s === 'bot' ? [] : s === 'top' ? ['neg', 'zero', 'pos'] : [s];
}

// 2. One combination: which signs can x + y have, if x has sign a and y has sign b?
function plusSigns(a: BasicSign, b: BasicSign): BasicSign[] {
  if (a === 'zero') return [b];               // 0 + y has the sign of y
  if (b === 'zero') return [a];
  if (a === b) return [a];                    // same signs: the sign stays
  return ['neg', 'zero', 'pos'];              // opposite signs: it depends on the sizes
}

// 3. Summarize the collected signs as one abstract value.
function summarize(signs: BasicSign[]): Sign {
  const distinct = new Set(signs);
  if (distinct.size === 0) return 'bot';
  if (distinct.size === 1) return signs[0];
  return 'top';                               // two or three signs: only ⊤ covers them
}

function plus(a: Sign, b: Sign): Sign {
  const results: BasicSign[] = [];
  for (const x of cases(a)) for (const y of cases(b)) results.push(...plusSigns(x, y));
  return summarize(results);
}
```

<Insight title="soundness of an abstract operator">

An abstract operator must never miss a concrete result:

> If $x \in \gamma(a)$ and $y \in \gamma(b)$, then $x \text{ op } y \in \gamma(a \text{ op}^\sharp b)$.

The result may contain extra values (imprecision), but must not miss one (that would be a bug). The **best** such operator is

$$
a \text{ op}^\sharp b = \alpha(\{\, x \text{ op } y \mid x \in \gamma(a),\ y \in \gamma(b) \,\})
\qquad\text{in short}\qquad f^\sharp = \alpha \circ f \circ \gamma
$$

Read right to left: go to sets, compute exactly, come back to the most precise abstract value. Splitting into cases is how we compute this for signs without enumerating infinite sets: γ is "split", the case table is "compute exactly, case by case", and α is "summarize". For richer domains we often settle for something sound but less than best, because the best operator is too expensive or not computable.

</Insight>

## Tests become filters

In chapter 2, a test like `x > 0` *filtered* the set of states. On signs it does the same, with the same recipe: split both sides into cases, and **keep only the cases in which the test can be true**.

Worked example, `x > 0` with `x` unknown ($\top$). The right side, `0`, covers only *zero*:

- Can a negative number be $> 0$? No. Drop *negative*.
- Can zero be $> 0$? No. Drop *zero*.
- Can a positive number be $> 0$? Yes. Keep *positive*.

So inside `if (x > 0) { … }`, `x` is $+$. Switch the calculator below to other tests:

- `x <= 0` keeps *negative* and *zero*, which summarizes as $\top$. On the `else` branch we learn nothing: the same "non-negative" gap as in the division table.
- `x == 0` keeps only *zero*.
- With `x` known to be $+$, the test `x < 0` keeps **no** case. The branch can never run: it is **unreachable** ($\bot$).

<CaseSplit a="top" op=">" b="zero" />

The code is the same loop, with a yes/no question instead of the arithmetic table:

```ts
refine(op, a, b) {
  const keepA: BasicSign[] = [], keepB: BasicSign[] = [];
  for (const x of cases(a)) for (const y of cases(b)) {
    if (canBeTrue(op, x, y)) { keepA.push(x); keepB.push(y); }  // e.g. canBeTrue('>', 'pos', 'zero')
  }
  return [summarize(keepA), summarize(keepB)];
}
```

`canBeTrue` answers questions like "can some positive be greater than zero?". The real code decides them by comparing the smallest and largest number of each basic sign: `x < y` is possible exactly when the smallest `x` is below the largest `y`.

Refinement only flows back into a variable when it appears bare in the comparison. For `x + 1 > 0` we learn something about the *value* of `x + 1` but don't push it back to `x`. Doing that ("backward abstract arithmetic") is a nice extension for later.

## Putting it together: the analyzer

An **abstract state** maps each variable to a sign, or is $\bot$ if the point is unreachable. The analyzer mirrors the interpreter of chapter 2 statement by statement, and solves the same equations with signs in place of sets:

| Statement | Interpreter (one state) | Analyzer (abstract state) |
| --- | --- | --- |
| `x = e` | evaluate `e`, store it | evaluate `e` with abstract operators, store it |
| `if (c) A else B` | run *one* branch | run **both**, on the state filtered by `c` and by `!c`, then **join** |
| `while (c) B` | repeat until `c` is false | repeat until the loop-head state **stops changing**, then filter by `!c` |
| `assert(c)` | crash if false | **proved** if `!c` filters to $\bot$, otherwise an alarm |

The loop is the interesting case. The loop head receives states from before the loop and from the end of the body, so we start from the entry state and keep joining in what the body produces:

```ts
let head = entry;
for (;;) {
  const bodyOut = exec(s.body, filter(head, s.cond));
  const next = joinEnv(entry, bodyOut);
  if (leqEnv(next, head)) break;       // nothing new: we have a loop invariant
  head = next;
}
const exit = filter(head, negate(s.cond));
```

Each pass can only move values up the lattice, and the sign lattice has height 2 ($\bot \to + \to \top$), so each variable changes at most twice. The loop **must** stop. Open "Loop iterations" under the playground to see the successive loop-head states.

<Insight title="why the loop terminates">

The loop computes the increasing sequence $H_0 \sqsubseteq H_1 \sqsubseteq H_2 \sqsubseteq \dots$ of loop-head states. In a lattice of **finite height** (no infinite strictly increasing chain) it must become stationary, and the limit is a fixpoint: a **loop invariant**, true every time execution reaches the loop head.

With $n$ variables and height-2 signs, there are at most $2n + 1$ iterations. Chapter 6 introduces intervals, a lattice of *infinite* height, where this argument fails and a new idea (widening) is needed.

</Insight>

## How the analyzer is built

Before trying it, step back and look at its shape. The analyzer has three layers, and each one only talks to the layer below it:

The **solver** is the table above: it knows `if`, `while` and `assert`, but nothing about signs. The **abstract state** is the "one sign per variable" map, plus ⊥, with the four operations the solver needs. Only the **value domain** knows what a sign is: everything in the first half of this chapter (the case tables, summarizing, tests as filters) lives there.

This split lets the rest of the course change one thing at a time. Later chapters show this picture again, with the layer they change highlighted:

- chapter 6: intervals, a value domain that forces the solver to handle loops differently;

## Where precision goes

Load **Countdown**, **Absolute value**, **Copy then subtract** and **Squares are non-negative**. Every assertion there is true, the testing tab finds no failure, and yet the analyzer reports "may fail". Each is a false alarm, and each has a different cause.

**1. The domain cannot express the property.** In *Countdown*, `y` starts at $0$ and becomes $+$ in the loop, so at the loop head it is $0 \sqcup + = \top$. The fact we need, $y \ge 0$, has no name in our lattice. Same for *Absolute value*: on the `else` branch, `x >= 0` refines $\top$ to “$0$ or $+$”, which rounds up to $\top$. *Fix: a richer domain* (exercise 3).

**2. Relations between variables are lost.** In *Copy then subtract*, `y = x` makes both $\top$, and $\top - \top = \top$. The analyzer forgot that `y` *is* `x`. In *Squares*, `x * x` is computed as "some $\top$ times some $\top$", as if the two operands were independent. *Fix: relational domains* (chapter 8), or smarter expression handling.

**3. The analysis is non-compositional with tests.** As noted above, `x + 1 > 0` does not refine `x`. *Fix: backward evaluation of expressions.*

There's a lesson here that holds for every analyzer. A false alarm doesn't mean the analyzer is broken. It means the abstraction is too coarse for that program. Choosing an abstraction that is cheap enough and precise enough is the main design work in abstract interpretation.

## Exercises

<Exercise n={1} title="analyze by hand">

Compute, by hand, the sign of every variable after each line, then check with the playground (paste it in).

```
a = input();
if (a < 0) {
  b = a * a;
  c = 0 - b;
} else {
  c = 5;
}
```

<Fragment slot="solution">

Line 1: `a` = $\top$. Inside the `then` branch, `a < 0` refines `a` to $-$; `b` = $- \times - = +$; `c` = $0 - (+) = -$. In the `else` branch `a >= 0` gives $\top$ (“$0$ or $+$” rounds up); `c` = $+$. After the `if`, join both branches: `a` = $- \sqcup \top = \top$, `b` = $+ \sqcup 0 = \top$ (b is still $0$ on the else branch), `c` = $- \sqcup + = \top$.

</Fragment>
</Exercise>

<Exercise n={2} title="spot the unsound table">

A colleague changes one case in `plusSigns`: positive + negative now returns only *positive* ("the bigger one usually wins"). Write a Tiny program on which the resulting analyzer proves an assertion that actually fails.

<Fragment slot="solution">

```
x = 1;
y = 0 - 5;
z = x + y;
assert(z > 0);
```

The analyzer computes `z` = $+$ and proves the assertion, but `z = -4`. The **Compare with testing** table would flag line 3 as **UNSOUND**: tests saw $-4$, whose sign $-$ is not below $+$. The project's unit tests check every operator against sample values for exactly this reason.

</Fragment>
</Exercise>

<Exercise n={3} title="a better sign domain">

Fix false-alarm cause 1 by adding three elements: $\ge 0$ ("non-negative"), $\le 0$ and $\ne 0$. Draw the new Hasse diagram (8 elements). What is $+ \sqcup 0$ now? Recompute $+ \div +$ and check that *Countdown* and *Absolute value* become provable. Which example remains unprovable, and why?

<Fragment slot="solution">

The elements are $\bot$; the three basic signs $-$, $0$, $+$; the pairs $\le 0$ (negative or zero), $\ne 0$ (negative or positive), $\ge 0$ (zero or positive); and $\top$. Each pair sits above its two basic signs and below $\top$, so the diagram looks like a cube's projection: it is the lattice of all subsets of the three basic signs.

$+ \sqcup 0 = {\ge 0}$, and $(+) \div (+) = {\ge 0}$ as well. In *Countdown*, the loop head has $y = 0 \sqcup + = {\ge 0}$, then $({\ge 0}) + (+) = +$, and the join is again $\ge 0$: stable, and `y >= 0` is proved. In *Absolute value*, the `else` branch refines `x` to $\ge 0$, and both branches give `y` $\ge 0$ or better.

*Copy then subtract* and *Squares* still fail: their problem is relational (cause 2), and no per-variable domain fixes it.

In code, this domain is *easier* than the 5-element one: an abstract value is exactly a **set of basic signs**, so `summarize` never has to round. Steps 1 and 2 of the recipe are unchanged; only step 3 differs. Chapter 4 implements exactly this domain and puts it next to the 5-element one.

</Fragment>
</Exercise>

<Exercise n={4} title="why not just ⊤?">

Inside a loop, the analyzer starts from the entry state and goes *up*. Why not start the loop head at $\top$ for every variable, which is certainly sound, and go down?

<Fragment slot="solution">

Starting at $\top$ is sound but throws away everything known before the loop, and going down from an over-approximation needs care to stay sound. Starting from below and going up until stable finds the **least** fixpoint: the most precise invariant those equations allow. In *Product of positives*, starting from $\top$ would lose the fact that `r` is positive. (Going down *after* reaching a fixpoint is a real technique, called narrowing; see chapter 6.)

</Fragment>
</Exercise>
